# QubitSphere — Circuit Intermediate Representation (Circuit IR)

## 1. Purpose

This document defines the official **Circuit Intermediate Representation (Circuit IR)** used by QubitSphere.

Circuit IR is the framework-neutral representation of a quantum circuit.

It provides a common format that can be understood by:

* Circuit Lab
* Circuit visualization
* Quantum execution layer
* Quantum simulators
* AI tutor
* Database
* Validation system
* Future quantum-framework adapters

The Circuit IR is a central architectural boundary in QubitSphere.

---

# 2. Core Principle

QubitSphere must not make the frontend directly dependent on a specific quantum-computing framework.

The intended flow is:

```text
Circuit Lab
    ↓
Circuit IR
    ↓
Execution Adapter
    ↓
Quantum Framework
    ↓
Simulator
    ↓
Normalized Result
```

The frontend creates and modifies the Circuit IR.

The execution layer converts the Circuit IR into the format required by the selected quantum framework.

This means the UI does not need to know whether the circuit is eventually executed by Qiskit, PennyLane, Cirq, or another backend.

---

# 3. Why Circuit IR Exists

Without a Circuit IR, different parts of the application could develop their own representations of the same circuit.

For example:

```text
Frontend representation
        ≠
Qiskit representation
        ≠
AI representation
        ≠
Database representation
```

That would make the system difficult to maintain.

Circuit IR provides one canonical logical representation:

```text
                Circuit IR
               /    |    \
              /     |     \
             ↓      ↓      ↓
        Simulator   AI   Visualization
```

All major systems can therefore reason about the same circuit.

---

# 4. Design Goals

The Circuit IR should be:

### Framework-neutral

It must not depend on Qiskit's internal object model.

### Serializable

It must be representable as JSON.

### Deterministic

The same valid Circuit IR should describe the same logical circuit.

### Extensible

New gates and metadata should be addable without breaking existing circuits.

### Validatable

The backend must be able to validate whether a Circuit IR is structurally valid.

### AI-readable

The AI tutor must be able to inspect the circuit in a predictable structure.

### UI-friendly

The Circuit Lab must be able to create, modify, and render it easily.

---

# 5. Canonical Circuit IR

The canonical top-level structure is:

```json
{
  "version": "1.0",
  "id": "optional-circuit-id",
  "name": "Bell State",
  "qubits": 2,
  "classicalBits": 2,
  "operations": [],
  "measurements": [],
  "metadata": {}
}
```

---

# 6. Top-Level Fields

## 6.1 `version`

Identifies the Circuit IR schema version.

Example:

```json
"version": "1.0"
```

The version allows the IR format to evolve in the future.

---

## 6.2 `id`

Optional unique identifier for the circuit.

Example:

```json
"id": "circuit-001"
```

The ID may be generated by the backend or database layer.

---

## 6.3 `name`

Human-readable circuit name.

Example:

```json
"name": "Bell State"
```

---

## 6.4 `qubits`

The number of quantum bits in the circuit.

Example:

```json
"qubits": 2
```

Valid qubit indexes range from:

```text
0
```

through:

```text
qubits - 1
```

For a 2-qubit circuit:

```text
q0
q1
```

---

## 6.5 `classicalBits`

The number of classical bits available for measurement results.

Example:

```json
"classicalBits": 2
```

This may be equal to the number of measured qubits in simple MVP circuits.

---

## 6.6 `operations`

An ordered list of quantum operations.

Example:

```json
"operations": [
  {
    "gate": "H",
    "targets": [0]
  },
  {
    "gate": "CX",
    "control": 0,
    "target": 1
  }
]
```

Operations must be executed in list order unless the execution layer explicitly defines another ordering mechanism.

---

## 6.7 `measurements`

Defines measurement operations or measurement targets.

For the MVP, this can be represented as a list of measured qubit indexes.

Example:

```json
"measurements": [0, 1]
```

Future versions may represent explicit measurement-to-classical-bit mappings.

---

## 6.8 `metadata`

Optional additional information.

Example:

```json
"metadata": {
  "lessonId": "entanglement-001",
  "algorithm": "bell-state",
  "difficulty": "beginner"
}
```

Metadata must not change the mathematical meaning of the circuit.

---

# 7. Operation Structure

Each item inside `operations` represents one circuit operation.

Basic structure:

```json
{
  "gate": "H",
  "targets": [0]
}
```

A more complete operation may contain:

```json
{
  "gate": "RX",
  "targets": [0],
  "parameters": {
    "theta": 1.5708
  }
}
```

Controlled operations may contain control qubits.

Example:

```json
{
  "gate": "CX",
  "control": 0,
  "target": 1
}
```

---

# 8. Operation Fields

## 8.1 `gate`

The canonical gate identifier.

Example:

```json
"gate": "H"
```

Gate identifiers must come from the supported gate registry.

They should use uppercase canonical names.

---

## 8.2 `targets`

List of qubits affected by the operation.

Example:

```json
"targets": [0]
```

For a gate affecting multiple qubits:

```json
"targets": [0, 1]
```

The meaning of target ordering must remain consistent for gates where ordering matters.

---

## 8.3 `control`

Optional control-qubit index.

Example:

```json
"control": 0
```

This is useful for controlled operations such as CX.

---

## 8.4 `parameters`

Optional numeric parameters.

Example:

```json
"parameters": {
  "theta": 1.5708
}
```

Parameters should be represented in a structured object rather than an unstructured string.

---

## 8.5 `position`

Optional circuit-grid position.

Example:

```json
"position": 2
```

The UI may use this field to preserve the visual time-step of an operation.

However, the mathematical meaning of a circuit must remain recoverable from the ordered operations.

---

## 8.6 `label`

Optional human-readable operation label.

Example:

```json
"label": "Hadamard"
```

This is primarily intended for presentation and educational purposes.

---

# 11. Multi-Qubit Gates

## 11.1 CX

Controlled-X gate, commonly called CNOT.

Example:

```json
{
  "gate": "CX",
  "control": 0,
  "target": 1
}
```

The control and target must be different valid qubit indexes.

---

## 11.2 Future Controlled Gates

Additional controlled gates may be added later.

Examples:

```text
CY
CZ
CRX
CRY
CRZ
```

These are not required for the initial MVP unless needed by an implemented algorithm.

---

# 12. Measurement

Measurement represents the process of reading quantum information.

For the MVP, the canonical representation is:

```json
"measurements": [0, 1]
```

This means that qubits 0 and 1 are measured.

A future version may support explicit measurement operations such as:

```json
{
  "gate": "MEASURE",
  "targets": [0],
  "classicalTarget": 0
}
```

However, the MVP should prefer the simpler representation unless explicit mapping is required.

---

# 13. Initial State

Unless otherwise specified, the circuit begins in the computational basis state:

```text
|0...0>
```

For example:

A one-qubit circuit begins in:

```text
|0>
```

A two-qubit circuit begins in:

```text
|00>
```

A future IR version may support configurable initial states.

---

# 14. Operation Ordering

Operations are logically applied in the order they appear.

Example:

```json
{
  "operations": [
    {
      "gate": "H",
      "targets": [0]
    },
    {
      "gate": "CX",
      "control": 0,
      "target": 1
    }
  ]
}
```

means:

```text
1. Apply H to q0
2. Apply CX with q0 as control and q1 as target
```

Operation order is therefore significant.

Reordering operations may change the meaning of the circuit.

# 15. Circuit Grid Position

For example:

```text
        0      1      2
q0 ─────H──────●──────M
               │
q1 ────────────X──────M
```

The grid positions may be represented with an optional `position` field.

Example:

```json
{
  "gate": "H",
  "targets": [0],
  "position": 0
}
```

and:

```json
{
  "gate": "CX",
  "control": 0,
  "target": 1,
  "position": 1
}
```

The visualization layer may use this information to render aligned operations.

# 19. Circuit Validation

Every Circuit IR received by the backend should be validated before execution.

Validation should check:

### Qubit count

`qubits` must be a positive integer.

### Classical-bit count

`classicalBits` must be a non-negative integer.

### Valid qubit indexes

Every referenced qubit must satisfy:

```text
0 <= index < qubits
```

### Valid gates

Every gate must exist in the supported gate registry.

### Required targets

Each gate must provide the correct number of targets.

### Control/target validity

For controlled gates:

```text
control != target
```

Both indexes must be valid.

### Parameters

Parameterized gates must contain required parameters.

Parameters must be numeric and within any required constraints.

### Measurement validity

Every measured qubit must be valid.

### Structure

The JSON must conform to the expected Circuit IR schema.

Invalid circuits must not be executed.

---

# 20. Validation Error Structure

The backend should return structured validation errors.

Example:

```json
{
  "valid": false,
  "errors": [
    {
      "code": "INVALID_QUBIT_INDEX",
      "message": "Qubit index 3 does not exist in a 2-qubit circuit.",
      "operationIndex": 1
    }
  ]
}
```

The frontend should be able to display understandable error messages to the learner.

---

# 21. Valid Circuit Response

For a valid circuit:

```json
{
  "valid": true,
  "errors": []
}
```

The execution layer can then proceed.

---

# 22. Simulation Input

The simulator should receive Circuit IR rather than raw frontend objects.

Conceptually:

```text
POST /api/circuit/simulate
        ↓
Circuit IR
        ↓
Validation
        ↓
Execution Adapter
        ↓
Qiskit
        ↓
Qiskit Aer
```

This ensures the simulator is insulated from frontend implementation details.

---

# 23. Simulation Result

Circuit IR defines the circuit itself.

It does not define one fixed simulation-result schema.

The execution system should return a normalized result that may include:

```json
{
  "success": true,
  "statevector": [],
  "probabilities": {},
  "counts": {},
  "shots": 1024
}
```

A result may contain additional fields when available.

For example:

```json
{
  "success": true,
  "probabilities": {
    "00": 0.5,
    "11": 0.5
  },
  "counts": {
    "00": 502,
    "11": 522
  },
  "shots": 1024
}
```

The values must come from the quantum execution layer.

# 28. Frontend Type Definition

The frontend should have an explicit TypeScript type for Circuit IR.

Conceptually:

```typescript
type CircuitIR = {
  version: string;
  id?: string;
  name?: string;
  qubits: number;
  classicalBits: number;
  operations: CircuitOperation[];
  measurements: number[];
  metadata?: Record<string, unknown>;
};
```

An operation may conceptually be represented as:

```typescript
type CircuitOperation = {
  gate: string;
  targets?: number[];
  control?: number;
  target?: number;
  parameters?: Record<string, number>;
  position?: number;
  label?: string;
};
```

These types should eventually be implemented in the actual shared type definitions.

---

# 29. Backend Model Definition

The FastAPI backend should have explicit validation models for Circuit IR.

Pydantic models should validate:

* Circuit structure
* Operation structure
* Gate names
* Parameters
* Qubit references
* Measurement references

The backend must not rely solely on frontend validation.

Frontend validation improves the user experience.

Backend validation protects the application.

---

# 30. Versioning

The Circuit IR must be versioned.

Initial version:

```text
1.0
```

Future breaking schema changes should create a new version.

For example:

```text
1.0
1.1
2.0
```

Minor versions may add backward-compatible fields.

Major versions may introduce breaking structural changes.

The execution layer should clearly define which versions it supports.

---

# 31. Backward Compatibility

The application should attempt to preserve compatibility with existing saved circuits when possible.

If an old Circuit IR requires migration, the system should use a migration step rather than silently interpreting it as a different circuit.

Conceptually:

```text
Stored Circuit IR
       ↓
Version Check
       ↓
Migration if Required
       ↓
Current Circuit IR
       ↓
Validation
       ↓
Execution
```

This is not required to be sophisticated in the MVP, but the version field should exist from the beginning.

---

# 32. Security and Trust Boundaries

Circuit IR is user-controlled input whenever a learner creates or uploads a circuit.

Therefore:

* Never trust frontend validation alone.
* Validate all circuit data on the backend.
* Reject unsupported operations.
* Reject invalid indexes.
* Enforce parameter constraints.
* Never execute arbitrary code supplied through Circuit IR.
* Do not allow Circuit IR to directly invoke shell commands or Python code.

The Circuit IR should describe quantum operations, not executable application code.

---

# 33. What Circuit IR Must NOT Contain

The canonical Circuit IR should not contain:

* Raw Python code
* Qiskit Python objects
* JavaScript executable code
* Shell commands
* API credentials
* Database credentials
* LLM prompts as executable instructions
* Framework-specific object serialization

The IR represents a quantum circuit, not application logic.

# 39. Non-Goals

The initial Circuit IR is not intended to fully represent every feature of every quantum framework.

The MVP does not require full support for:

* Arbitrary custom unitary matrices
* Pulse-level programming
* Hardware calibration data
* Dynamic circuits
* Mid-circuit classical control
* Advanced noise models
* Hardware-specific gates
* OpenQASM-specific implementation details
* Pulse schedules
* Quantum error-correction instruction sets

These may be introduced in future versions if required.

---

# 40. Design Rule for Future Extensions

When adding a new quantum capability, ask:

> Can this capability be represented cleanly in the framework-neutral Circuit IR?

If yes, extend the IR carefully.

If the capability requires framework-specific information, keep that information inside the execution adapter rather than leaking it into the core Circuit IR unless the information is fundamentally part of the logical circuit.

---

# 41. Circuit IR Source of Truth

The following rule applies throughout QubitSphere development:

> **Circuit IR is the canonical logical representation of a QubitSphere circuit.**

No other representation should become the primary source of truth.

Framework-specific circuit objects are derived representations.

Visualization objects are derived representations.

AI-readable summaries are derived representations.

Simulation results are outputs derived from the Circuit IR.

---

# 42. Final Architecture Rule

QubitSphere follows this principle:

```text
             CIRCUIT IR
                 │
        ┌────────┼────────┐
        ↓        ↓        ↓
     Execute   Explain  Visualize
        │        │        │
     Quantum     AI       UI
     Engine     Tutor    Renderer
```

The Circuit IR connects the major systems while keeping them independent.

The most important rule is:

> **The Circuit Lab creates the circuit, Circuit IR represents the circuit, the quantum engine calculates the result, and the AI explains the verified result.**

That separation must be preserved throughout the implementation of QubitSphere.
